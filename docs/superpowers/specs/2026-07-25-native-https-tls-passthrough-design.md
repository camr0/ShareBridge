# Native HTTPS TLS-Passthrough Architecture

**Date:** 2026-07-25
**Status:** Proposed — pending final review
**Supersedes for migrated shares:** WebRTC transfer channels, Secure Relay/Noise browser channels, multilane transfer framing, and service-worker-simulated HTTP media delivery
**Preserves:** Native-share discovery, source connectors, share lifecycle, gallery construction, passwords, source authorization, account/control-plane functionality, and the recipient-facing ShareBridge product

## 1. Summary

ShareBridge will migrate its bulk data plane from a custom browser transfer protocol to ordinary browser HTTPS.

The recipient will continue opening the native-looking link generated by the source application:

```text
https://sharebridge.app/share/<immich-key>
https://sharebridge.app/s/<nextcloud-or-opencloud-token>
```

The ShareBridge control plane will resolve that native share to a one-time, share-specific content origin:

```text
https://<share-origin>.<agent-namespace>.sharebridgeusercontent.com/<native-route>
```

The browser will establish normal HTTPS directly with a web server running inside the local ShareBridge agent. A public Layer 4 gateway will inspect only the TLS ClientHello/SNI hostname and forward the raw encrypted TCP stream through an authenticated FRP tunnel. The gateway will not terminate browser TLS and will not be able to read HTTP, passwords, files, photos, videos, document contents, cookies, or editor traffic.

Each agent will own a wildcard certificate for a random, replaceable public certificate namespace:

```text
*.<agent-namespace>.sharebridgeusercontent.com
```

Each native share will receive one random child hostname under that namespace:

```text
<share-origin>.<agent-namespace>.sharebridgeusercontent.com
```

The gateway will route only exact, active share hostnames. It will not route the bare agent namespace or arbitrary wildcard children. When a native share is deleted, revoked, or expired, its exact mapping will be removed and active streams will be terminated. The hostname will be permanently tombstoned and never reused.

This design preserves ShareBridge's key security property:

> Public network reachability exists only for an explicitly shared resource and only while that resource remains shared.

## 2. Motivation

ShareBridge began as a primarily peer-to-peer WebRTC product with TURN fallback. TURN was later replaced by a custom end-to-end encrypted Secure Relay. Relay subsequently became the default because it hides the home IP address and is more reliable than browser WebRTC.

That evolution left ShareBridge maintaining a custom browser data plane for a use case that is now fundamentally relay-oriented:

- WebRTC negotiation and ICE behavior
- Noise handshakes in browser JavaScript
- Secure Relay WebSockets
- binary message envelopes
- logical transfer lanes
- lane scheduling and backpressure
- service-worker bridges that make transferred media resemble HTTP
- custom Range request and video-seek coordination
- reconnect races and transport selection

The current implementation works, but it reimplements behavior that browsers, HTTP servers, and reverse proxies already provide natively.

Moving to browser-native HTTPS provides:

- ordinary HTTP request/response semantics
- native HTTP Range requests and `206 Partial Content`
- reliable video streaming and seeking
- browser-managed cancellation and retry
- standard caching and conditional requests
- standard downloads and download managers
- HTTP/2 multiplexing
- ordinary WebSockets
- simpler uploads
- a viable path to Collabora and ONLYOFFICE
- fewer browser-specific service-worker workarounds
- a smaller application protocol
- easier compatibility with future source applications

The transport becomes simpler while the ShareBridge product remains source-aware.

## 3. Product Boundary

ShareBridge is not intended to become a generic public reverse proxy like ngrok, zrok, Pangolin, or Cloudflare Tunnel.

Its product promise remains:

> Select an album, folder, file, or document in the self-hosted application you already use; send its normal link; let any recipient use it naturally in a browser without a VPN, installed client, exposed home IP, or knowledge of networking.

ShareBridge understands:

- the native source share
- its lifecycle
- its password and permissions
- the resource being shared
- the recipient experience
- future external identities and roles

The tunnel is an implementation detail. Users do not select ports, protocols, directories, or arbitrary local services.

## 4. Goals

- Serve recipient content over ordinary browser HTTPS.
- Terminate recipient TLS only inside the owner's agent.
- Keep ShareBridge infrastructure unable to decrypt recipient content.
- Preserve a single global native-link base at `sharebridge.app`.
- Preserve Immich `/share/<key>` and OpenCloud/Nextcloud `/s/<token>` link shapes.
- Hide the home IP address and require no inbound home firewall rule.
- Give each native share an exact, revocable network route.
- Ensure a revoked share can no longer cause traffic to reach the home agent.
- Avoid a stable, generally routable public endpoint for an agent.
- Reuse one agent wildcard certificate for unlimited per-share origins.
- Keep source applications authoritative for native share lifecycle.
- Preserve existing connector, gallery, asset, password, and ZIP work.
- Support public, password-protected, and future identity-restricted shares.
- Support HTTP Range, uploads, and WebSockets without custom browser framing.
- Create a credible foundation for Collabora/ONLYOFFICE.
- Keep the hosted and fully self-hosted variants architecturally equivalent.
- Migrate incrementally while the current Secure Relay remains available.

## 5. Non-Goals

- Exposing arbitrary home-server applications or ports.
- Giving recipients network-level access to the owner's LAN.
- Replacing Tailscale, OpenZiti, zrok, or a general zero-trust network.
- Making hostnames secret credentials.
- Preventing recipients from retaining content they already downloaded.
- Hiding that a hostname belongs to ShareBridge from Certificate Transparency.
- Cloud-native guest/OIDC provisioning in the first transport migration.
- Collabora/ONLYOFFICE implementation in the first transport migration.
- Removing the current data plane before native HTTPS reaches functional parity.
- Building a multi-region relay fabric in the first release.
- Splitting every logical module into a separately deployed microservice.

## 6. High-Level Architecture

```text
                                CONTROL PLANE

Source app                    ShareBridge control                Public CA
Immich/NC/OC                  sharebridge.app
    │                               │                                │
    │ native share lifecycle        │ agents, shares, origins        │
    ▼                               │ policy, abuse, enrollment      │
Local agent ◄── authenticated ─────►│ certificate jobs ─────────────►│
    │        control channel        │ route distribution              │
    │                               │                                │


                                  DATA PLANE

Recipient browser
    │
    │ TLS encrypted for agent-owned certificate
    ▼
Public SNI gateway
    │ inspect: source IP, SNI, timing, bytes
    │ cannot inspect: HTTP, cookies, passwords, content
    ▼
FRP server
    │ authenticated outbound tunnel
    ▼
Local ShareBridge agent
    │ terminates browser TLS
    │ serves native HTTP application
    ▼
Private Immich / Nextcloud / OpenCloud / Collabora
```

### 6.1 Server-Side Responsibilities

The hosted system has three logical server-side responsibilities:

1. **ShareBridge control plane**
   - accounts and API keys
   - agent enrollment
   - native-share persistence
   - canonical native-link routes
   - certificate namespace allocation
   - per-share origin allocation
   - share-origin lifecycle
   - tunnel authorization
   - abuse policy
   - route distribution

2. **Certificate coordinator**
   - agent CSR processing
   - ACME provider selection
   - DNS-01 automation
   - issuance and renewal
   - CA fallback
   - certificate inventory
   - Certificate Transparency monitoring
   - unexpected-issuance alerts

3. **TLS/FRP data plane**
   - public TCP listener
   - ClientHello/SNI parsing
   - exact-host route lookup
   - pre-tunnel blocking and rate limiting
   - authenticated FRP tunnel transport
   - connection and byte reporting
   - active-stream termination after revocation

These are logical boundaries, not a requirement for three custom microservices in the first implementation.

## 7. Identifiers and Namespaces

ShareBridge must not reuse one identifier for several trust domains.

### 7.1 Internal Account ID

An internal database identifier. Never placed in DNS names or certificates.

### 7.2 Internal Agent ID

A stable identifier used by the control protocol, database relationships, logs, and tunnel enrollment. Never intentionally exposed to recipients.

### 7.3 Public Agent Certificate Namespace

A long, cryptographically random, replaceable value:

```text
v7q4km2x9pz6dn3w
```

It contains:

- no username
- no email
- no sequence number
- no account ID
- no internal agent ID
- no hardware identifier

The namespace exists primarily so one agent-owned wildcard certificate can cover unlimited per-share origins:

```text
*.v7q4km2x9pz6dn3w.sharebridgeusercontent.com
```

The namespace is public metadata, not a secret. It appears in DNS, browser connections, and Certificate Transparency.

### 7.4 Share Origin ID

A long random value assigned exactly once:

```text
r7k2m9p4x6
```

The full origin is:

```text
r7k2m9p4x6.v7q4km2x9pz6dn3w.sharebridgeusercontent.com
```

Rules:

- one origin is permanently bound to one native share
- an origin is never reassigned
- deletion produces a permanent tombstone
- the origin contains no service type
- the origin alone is not the bearer credential
- the gateway routes only an exact active origin

### 7.5 Native Share Code

The bearer capability created by the source application:

```text
Immich:              /share/<key>
Nextcloud/OpenCloud: /s/<token>
```

For a public share, possession of the native share code authorizes viewing according to source policy.

For a protected share, access requires:

```text
native share code + native share password
```

The control plane treats the public route identity as:

```text
(route kind, native share code)
```

so Immich `/share/<key>` and file-cloud `/s/<token>` do not collide merely because their token strings happen to match.

Two source instances that independently generate the same token under the same route kind cannot both own the same global canonical URL. The first connector-verified registration retains the mapping; a conflicting registration is rejected without overwriting or revealing the existing owner. Registration requires source-connector proof, not mere possession of a copied public token, to prevent claim squatting.

### 7.6 Future ShareBridge Identity Grant

Future authenticated operations may additionally require a short-lived ShareBridge grant:

```text
native share + verified recipient + role + expiration
```

This is not required for ordinary public or password-protected native shares.

## 8. DNS and Hostname Design

The content domain is separate from the ShareBridge control-plane domain:

```text
sharebridge.app
sharebridgeusercontent.com
```

The separate registered domain provides stronger browser site isolation for:

- cookies
- `SameSite` behavior
- service workers
- storage
- proxied third-party application HTML
- future office editor content

The expected hostname shape is:

```text
<share-origin>.<agent-namespace>.sharebridgeusercontent.com
```

Service labels such as `files.` and `office.` are not required. The route table already identifies the share type and assigned resource.

The DNS design must allow arbitrary children beneath an enrolled agent namespace without a DNS mutation during share creation. This may use:

- a wildcard DNS record per enrolled agent namespace, created during certificate enrollment, or
- an authoritative wildcard-routing DNS design proven to resolve the required nested names

DNS readiness is part of agent enrollment, not share creation.

## 9. Certificate Architecture

### 9.1 Ownership

The agent generates and stores its TLS private key locally.

The private key never leaves the agent.

The agent produces a CSR for:

```text
*.<agent-namespace>.sharebridgeusercontent.com
```

The certificate coordinator completes DNS-01 validation and returns only the public certificate chain.

### 9.2 Enrollment Flow

```text
Agent                              Control plane / CA coordinator
  │
  ├─ generate private key
  ├─ generate wildcard CSR
  │
  ├──────── CSR ─────────────────────────►
  │                                      ├─ validate enrollment
  │                                      ├─ choose ACME provider
  │                                      ├─ create DNS-01 record
  │                                      ├─ finalize order with CSR
  │                                      └─ remove challenge record
  │
  ◄──────── certificate chain ────────────┤
  │
  ├─ verify SAN
  ├─ verify certificate public key
  ├─ verify trust chain and validity
  ├─ store certificate atomically
  └─ report TLS readiness
```

The control plane activates share routes only after the agent confirms that it can serve the expected certificate.

### 9.3 Renewal

The coordinator monitors expiration and begins renewal early.

```text
renewal window opens
→ coordinator requests CSR from connected agent
→ agent may reuse or rotate its local key according to policy
→ coordinator performs ACME DNS-01
→ agent validates and atomically reloads certificate
→ old certificate remains available until new certificate is active
```

An agent being temporarily offline must not immediately cause an outage. Renewal starts with sufficient safety margin and retries with bounded backoff.

### 9.4 CA Provider Abstraction

Certificate issuance is hidden behind a provider-neutral interface:

```text
Issue CSR
Renew certificate
Revoke certificate
Report provider status
```

Initial candidate providers:

1. ZeroSSL, subject to explicit confirmation of high-volume free/low-cost ACME use
2. Google Trust Services Public CA
3. Let's Encrypt as fallback, development provider, or primary after a rate-limit override
4. A negotiated commercial CA for future scale or SLA requirements

The provider abstraction is not part of FRP. Certificate issuance occurs over the authenticated control plane before live browser traffic is routed.

### 9.5 CA Constraints

The implementation must account for:

- publicly trusted roots
- wildcard support through DNS-01
- per-domain and per-account issuance limits
- order and authorization quotas
- provider terms for hosted high-volume use
- certificate lifetime reductions
- automated renewal
- ACME Renewal Information where supported
- CA outages
- chain compatibility across browsers and operating systems
- CAA authorization for every configured CA

Let's Encrypt's default limit of 50 new certificates per registered domain per seven days would limit ShareBridge to approximately 50 newly certified agents per week. This default is not acceptable as the only production path.

Google Public CA currently documents high-volume support, wildcard DNS-01, and a default quota of 100 certificate orders per hour. ZeroSSL currently advertises unlimited free ACME certificates and no comparable registered-domain limit. Both claims require a production-oriented spike and terms review before the architecture is committed to either provider.

### 9.6 Certificate Transparency

Public certificates and wildcard namespaces will appear in Certificate Transparency.

Therefore:

- the agent namespace is never treated as secret
- the share origin is never treated as the only bearer credential
- CT scraping must not expose a native share code
- unmapped hostnames receive a generic edge rejection
- the bare namespace and arbitrary child names are never routed
- unexpected issuance is monitored and alerted

CT reveals the wildcard namespace and allows cross-share correlation through the common suffix. It does not reveal:

- the native share code
- the source application
- the source hostname
- the home IP
- the owner identity
- the content

### 9.7 Control-Plane Certificate Trust Limitation

Because ShareBridge controls the parent DNS domain, a compromised ShareBridge certificate coordinator could complete domain validation using an attacker-controlled key and obtain another valid certificate for an agent namespace.

This is inherent to WebPKI domain control and cannot be removed by changing CAs.

Mitigations:

- isolate DNS and ACME credentials from the general web process
- use least-privilege DNS credentials
- authorize only selected CAs through CAA
- maintain an append-only issuance log
- monitor Certificate Transparency
- alert agents and operators on unexpected issuance
- expose an agent verification command
- document that the browser still trusts the ShareBridge-controlled DNS authority

The guarantee is therefore:

> Under normal operation, ShareBridge infrastructure does not possess agent TLS private keys and cannot decrypt content.

It is not:

> A malicious domain owner is cryptographically incapable of obtaining a replacement certificate.

## 10. Canonical Link and Content Navigation

The source application generates only the configured generic ShareBridge base:

```text
https://sharebridge.app/share/<immich-key>
https://sharebridge.app/s/<cloud-token>
```

ShareBridge does not require source applications to know an agent namespace or share origin.

### 10.1 Public Share

```text
Recipient
→ GET sharebridge.app/share/<native-key>
→ control plane resolves active registered share
→ 302 to:
   https://<share-origin>.<agent-namespace>.sharebridgeusercontent.com/share/<native-key>
→ gateway routes exact SNI to agent tunnel
→ agent verifies Host + route kind + native key binding
→ agent validates source share remains active
→ agent serves content
```

No ShareBridge one-time token is required. The native share code is already the bearer capability.

### 10.2 Password-Protected Share

```text
Recipient opens native link
→ redirects to assigned content origin with native code
→ agent determines source share is password-protected
→ agent serves password form
→ browser submits password directly over browser-to-agent TLS
→ agent asks source application to validate it
→ source accepts or rejects
→ agent creates a local authenticated session on success
```

The signaling/control server never receives the raw password.

This removes the current Immich exception in which a raw password transits the signaling server.

### 10.3 No Redundant Bootstrap Token

An extra one-time bootstrap capability is not required for public/password native shares because:

- the native share code is already the capability
- the gateway cannot inspect HTTP inside passthrough TLS
- an extra token would not prevent TLS handshakes from reaching the agent
- it would duplicate source authorization

Future ShareBridge identity grants remain appropriate for uploads, editing, named recipients, and per-recipient revocation.

## 11. Strict Origin-to-Share Binding

The gateway and agent independently enforce binding.

### 11.1 Gateway Binding

The active route table contains:

```text
exact SNI hostname
→ tunnel identity
→ internal agent ID
→ internal share ID
→ status and limits
```

The gateway does not route:

- the bare agent namespace
- wildcard matches without an exact active share record
- tombstoned share origins
- unknown hostnames

### 11.2 Agent Binding

The agent accepts only the exact configured tuple:

```text
(Host, route kind, native share code)
```

Example:

```text
r7k2... + /share/IMMICH123 → allowed
r7k2... + /share/OTHER456  → reject
r7k2... + /s/CLOUD789      → reject
other-host + IMMICH123     → reject
```

The agent must also reject:

- arbitrary local proxy targets
- absolute-form URLs selecting another host
- unapproved methods
- attempts to select another connector
- source redirects that reveal or target private hostnames
- malformed or duplicated `Host` values
- hostnames not present in agent-local signed route state

The agent is never a generic reverse proxy.

## 12. Share-Origin Lifecycle

### 12.1 Allocation

When the agent discovers a new native share:

1. The agent registers the source share through the control channel.
2. The control plane verifies ownership and source type.
3. The control plane allocates a random child hostname under the agent namespace.
4. The mapping is pushed to the gateway and agent.
5. Both sides acknowledge the same mapping version.
6. The route becomes active.

No DNS or certificate operation occurs during share creation.

### 12.2 Active

One origin remains assigned for the entire native-share lifetime, even for a long-lived share.

Rotating origins while the native share code remains active does not protect against a recipient who possesses the canonical link; that recipient can simply reopen the link and discover the replacement origin.

Therefore multiple rotating origins per long-lived share are not part of the design.

### 12.3 Revocation

When polling or source validation determines that a native share was deleted, expired, or revoked:

```text
agent stops serving share locally
→ agent reports revocation
→ control plane marks share revoked
→ control plane deletes exact gateway route
→ gateway rejects new connections
→ gateway terminates matching active streams
→ origin is permanently tombstoned
```

The route must fail closed if control-plane and agent state disagree.

### 12.4 Polling Delay

Source applications remain authoritative, but polling introduces eventual consistency.

The agent must revalidate source authorization on new HTTP sessions and sensitive operations. Gateway route removal follows the next poll/report. A deleted source share must not continue serving merely because the public route has not yet been removed.

### 12.5 Tombstones

Tombstones prevent:

- old bookmarks reaching unrelated future content
- stale DNS/cache state being reinterpreted
- accidental hostname reassignment
- share-origin collision recovery that silently changes ownership

Random origin space is sufficiently large that reuse is unnecessary.

## 13. Data Plane

### 13.1 Public SNI Gateway

The gateway:

- listens on public TCP 443
- accepts a connection
- reads only enough TLS ClientHello bytes to determine SNI
- records the source IP
- performs exact active-route lookup
- applies pre-tunnel policy
- opens the associated FRP stream
- forwards bytes bidirectionally

It does not:

- terminate TLS
- possess agent certificate keys
- parse HTTP
- inject HTTP headers
- authenticate passwords
- rewrite content

### 13.2 FRP

FRP provides the authenticated outbound tunnel between the public data plane and local agent.

The intended abstraction is:

```text
Open stream to tunnel identity
Forward raw TCP bidirectionally
Close stream
Report connection status and byte counts
```

FRP is replaceable. ShareBridge application code must not depend on FRP protocol details outside a narrow tunnel interface.

Future replacements could include OpenZiti or another transport without changing connectors, identities, or recipient HTTP behavior.

### 13.3 Route Distribution

The gateway must not query the primary database for every TCP connection.

The control plane pushes:

- versioned route snapshots
- incremental additions
- revocations
- limit changes
- block updates

The gateway maintains an in-memory exact-host table and fails closed if route state is missing or invalid.

Single-node v1 may use an authenticated internal API or local event channel. A distributed route bus is deferred until required by multi-node deployment.

### 13.4 Client IP

The public gateway is authoritative for the observed source IP.

The system should correlate agent reports using a gateway-generated connection ID rather than trusting an agent-supplied arbitrary IP.

Possible mechanisms:

- PROXY protocol v2 before the agent TLS stream, with the agent explicitly parsing it before TLS
- an authenticated side-channel mapping of connection ID to source IP
- FRP metadata support proven not to alter browser TLS bytes

The selected mechanism must preserve raw browser TLS after any explicitly defined preamble and must not permit an agent to poison global reputation for an arbitrary IP.

## 14. Abuse and DoS Controls

End-to-end TLS prevents the gateway from inspecting application requests, but it does not make the gateway blind.

The gateway observes:

- source IP
- SNI hostname
- connection start and duration
- TLS handshake frequency
- concurrent connections
- bytes in each direction
- tunnel/agent availability

The gateway can enforce:

- connections per IP
- connections per share origin
- concurrent streams per IP/origin/agent
- handshake rate
- connection idle timeout
- byte and bandwidth quotas
- temporary source-IP blocks
- circuit breaking for an overloaded/offline agent

The agent reports semantic failures:

- wrong password
- invalid native code
- expired source share
- invalid identity grant
- unauthorized method
- repeated invalid asset access

Reports travel over the authenticated control channel and reference the gateway connection ID.

Default automatic blocks are scoped to:

```text
(source IP, share origin)
```

They may optionally escalate to:

```text
(source IP, agent)
```

after corroborated abuse.

One agent must never be able to blacklist an IP across unrelated agents. Platform-global reputation requires independent gateway evidence or multi-agent corroboration.

Blocks use progressive temporary TTLs rather than permanent IP bans because of CGNAT, shared networks, and IPv6 rotation.

Agent reports cannot prevent the first request from reaching the agent. Generic edge limits apply independently before any report.

## 15. Agent HTTPS Server

The local agent becomes the authoritative recipient web server.

Responsibilities:

- TLS termination
- `Host` and share binding
- gallery/file UI delivery
- password forms and source validation
- manifests and metadata
- thumbnails
- original assets
- HTTP Range
- HEAD requests
- ZIP downloads
- uploads where permitted
- WebSockets
- future office proxying
- local session cookies
- security headers

The server talks to source applications over their private LAN URLs.

### 15.1 Browser Assets

The recipient frontend should be packaged with the agent so the content origin can serve a self-contained application without fetching sensitive data through `sharebridge.app`.

Build-time static assets may be shared across connectors, but source-specific data and authenticated requests remain on the agent content origin.

### 15.2 HTTP Semantics

The agent uses native HTTP behavior:

- `GET`
- `HEAD`
- `Range`
- `206 Partial Content`
- `Content-Range`
- `Accept-Ranges`
- `Content-Length`
- conditional requests where useful
- standard request cancellation
- streaming response bodies

The service worker is no longer responsible for simulating HTTP media over a message channel.

### 15.3 Cookies

Content-origin cookies:

- are host-only
- use the `__Host-` prefix where applicable
- use `Secure`
- use `HttpOnly` when JavaScript access is unnecessary
- use an explicit `SameSite` policy
- never use `Domain=sharebridgeusercontent.com`
- never use `Domain=sharebridge.app`

The control plane and content domain are different registered sites.

Content responses also use a restrictive `Referrer-Policy` so native share codes are not disclosed to unrelated external origins through browser referrers.

## 16. Source Connectors

The source connector remains the only component allowed to contact the private source service.

### 16.1 Immich

Preserved:

- native `/share/<key>` links
- shared-link polling
- gallery manifests
- thumbnails and originals
- password validation through Immich
- album ZIP
- lifecycle reconciliation

Changed:

- browser password submits directly to agent HTTPS
- assets use ordinary HTTP
- videos use native Range
- no Secure Relay transfer protocol

### 16.2 Nextcloud and OpenCloud

The intended future connector model remains native-share-first:

```text
native mobile/web share
→ agent discovers share through source API
→ agent registers native token
→ ShareBridge exposes native-looking link
```

Existing extensions may remain available during migration. They are not deleted until API-driven native-share flows are proven.

### 16.3 Immich Public Proxy

Immich Public Proxy remains:

- a security reference
- a route-minimization benchmark
- a possible optional tunnel target

It is not embedded as the default ShareBridge implementation because ShareBridge requires a unified multi-backend policy, identity, telemetry, and presentation model.

## 17. Future Office Support

Native HTTPS makes Collabora/ONLYOFFICE feasible because the browser can use:

- ordinary iframe loading
- normal HTTP
- WebSockets
- cookies
- redirects
- editor asset loading

Potential flow:

```text
Recipient browser
→ one-time office share origin
→ agent application proxy
→ private Collabora
↔ private WOPI
→ private OpenCloud/Nextcloud
```

The office origin is still bound to one specific document/share and authorization policy. The agent is not a generic proxy to the complete office server.

Future authenticated editing may add:

- ShareBridge login
- verified email identity
- short-lived signed role grants
- source guest/OIDC mapping
- source-cloud ACLs
- per-recipient revocation

Those features build on the transport but are outside its first migration.

## 18. Deployment Boundaries

### 18.1 Initial Hosted Deployment

One VPS may run:

```text
sharebridge-control
├── HTTP/API/control WebSockets
└── certificate coordinator worker

sharebridge-gateway
└── public SNI routing and edge limits

frps
└── authenticated tunnel transport

database
└── control-plane state
```

The gateway and FRP server are separate processes from the control plane because they carry bulk traffic and need independent resource limits.

The certificate coordinator begins as a logically isolated worker/module. It may later become a separate deployed service to isolate DNS and CA credentials.

### 18.2 Agent Deployment

```text
sharebridge-agent
├── authenticated control connection
├── embedded or managed frpc
├── local TLS private key and certificates
├── native HTTPS server
├── share-origin binding table
└── source connectors
```

The user still installs one ShareBridge agent.

### 18.3 Fully Self-Hosted Deployment

Self-hosters receive the same architecture in a compact Docker Compose deployment.

The design must not require:

- Kubernetes
- RabbitMQ
- OpenZiti
- a separate externally operated identity provider
- Cloudflare TLS termination

External CA use remains necessary for ordinary browser trust unless the self-hoster supplies their own public domain/certificate workflow.

## 19. Migration Strategy

This is a major data-plane replacement, not a ground-up ShareBridge rewrite.

### 19.1 Parallel Implementation

Keep both transports:

```text
Legacy:
browser → Secure Relay/WebRTC → agent transfer protocol

New:
browser → native HTTPS → SNI gateway/FRP → agent HTTP server
```

Use a server-authoritative feature flag or per-share transport mode.

### 19.2 Proof Sequence

Before migrating production behavior:

1. Prove wildcard certificate issuance with an agent-generated private key.
2. Prove renewal and atomic reload.
3. Prove nested wildcard DNS behavior.
4. Prove raw TLS passthrough through the selected FRP topology.
5. Confirm gateway cannot decrypt browser HTTP.
6. Prove exact SNI mapping and tombstone rejection.
7. Prove HTTP/1.1 and HTTP/2 behavior.
8. Prove Range seeking in Chrome, Safari, and Firefox.
9. Prove long-lived WebSockets.
10. Prove client-IP correlation and edge blocking.
11. Prove route deletion prevents any new stream from reaching agent.

### 19.3 Connector Migration

Recommended order:

1. Immich, because video seeking most clearly benefits
2. Nextcloud
3. OpenCloud after its native-share connector prerequisites are proven
4. upload flows
5. Collabora/ONLYOFFICE spike

### 19.4 Removal Criteria

Do not delete the legacy data plane until:

- migrated connector parity is documented
- real mobile native-share flows pass
- password-protected shares pass
- revocation passes
- Range and seek pass across supported browsers
- ZIP and downloads pass
- abuse controls pass
- clean install and upgrade pass
- rollback has been exercised

After parity, remove:

- browser WebRTC peer creation
- SecureRelayChannel
- browser Noise framing
- multilane transfer protocol
- lane scheduler
- binary envelopes used only by the old transport
- service-worker media bridge
- custom Range/seek coordination
- legacy transfer WebSocket payload routing

Preserve any shared code still used outside the old transport.

## 20. Failure Handling

### 20.1 Agent Offline

The gateway does not forward to an unavailable tunnel. The canonical page reports the agent is offline without exposing additional routing information.

### 20.2 Route Not Yet Registered

A newly created native share may be opened before the next source poll. The canonical page may show a bounded "preparing share" state and retry registration lookup. Unknown shares still fail generically after timeout.

### 20.3 Certificate Not Ready

Agent enrollment is incomplete until certificate and DNS readiness pass. Existing shares remain on the legacy transport during migration rather than publishing a broken native-HTTPS route.

### 20.4 CA Outage

Existing certificates continue working. New enrollment and renewal jobs retry using provider policy. Fallback to another CA is allowed only when CAA and provider configuration authorize it.

### 20.5 Control Plane Unavailable

The data plane may continue serving already-distributed active routes for a short, configured grace period. Security-sensitive revocation requirements may instead choose fail-closed expiration of route leases.

Route leases must be finite so a permanently disconnected gateway cannot serve stale shares indefinitely.

### 20.6 Gateway Restart

The gateway loads a signed/versioned route snapshot before accepting public traffic. It rejects connections until route state is ready.

### 20.7 Agent/Control Disagreement

The agent performs source authorization independently. A stale gateway route cannot force an agent to serve a deleted share.

### 20.8 Renewal Failure

Renewal alerts escalate before expiration. The agent retains the last valid certificate until it expires and never installs a certificate whose SAN or public key does not match expectations.

## 21. Security Properties

### 21.1 Provided

- No inbound home firewall rule.
- Home IP hidden from recipients.
- Browser content encrypted to agent-owned key.
- Gateway content opacity under normal operation.
- Exact per-share network routing.
- Edge-level revocation after share deletion.
- No generally routable agent hostname.
- No hostname reuse.
- Strict agent-side origin/share binding.
- Source application remains authoritative.
- Gateway blocks before tunnel based on IP/SNI metadata.
- Passwords travel directly to agent, not through control-plane plaintext.

### 21.2 Not Provided

- Protection from malicious JavaScript served by a compromised control plane before redirect.
- Cryptographic prevention of DNS-domain owner certificate mis-issuance.
- Protection against content already downloaded.
- Complete concealment of share existence from timing or CT metadata.
- Prevention of all traffic reaching an agent while a recipient has a valid active share.
- Volumetric DDoS protection beyond the public hosting provider's capacity.
- Protection for unrelated services the owner independently exposes outside ShareBridge.

### 21.3 Active-Share Reachability

While a share is active, someone who knows its exact content origin can perform a TLS handshake against the agent through the gateway even without the native code. They cannot retrieve content without the native code and any required password/identity.

This is bounded by:

- one share-specific origin
- edge rate limits
- source-IP blocking
- agent rejection
- complete route removal on revocation

Multiple origins or origin rotation do not improve security against a recipient who retains the canonical native link while the share remains active.

## 22. Testing Strategy

### 22.1 Certificate Tests

- agent private key never reaches server
- CSR public key matches installed certificate
- wildcard SAN is exact
- wrong namespace is rejected
- provider fallback follows policy
- DNS challenge cleanup occurs
- renewal atomically replaces certificate
- expired and malformed certificates fail closed
- unexpected CT issuance triggers alert

### 22.2 Gateway Tests

- exact SNI route succeeds
- bare agent namespace fails
- random child under known namespace fails
- tombstoned origin fails
- revoked route terminates active streams
- unknown SNI receives generic rejection
- malformed ClientHello is bounded and rejected
- source-IP limits apply before tunnel
- gateway never receives agent private key

### 22.3 Agent Binding Tests

- correct Host/code/type succeeds
- wrong code on correct origin fails
- correct code on wrong origin fails
- alternate connector route fails
- arbitrary target/SSRF attempts fail
- source redirect cannot expose private host
- unapproved methods fail

### 22.4 HTTP Tests

- GET and HEAD
- single and suffix Range
- invalid/unsatisfiable Range
- cancellation during streaming
- seeking forward and backward
- concurrent asset requests
- ZIP streaming
- upload limits
- WebSocket upgrade
- HTTP/2 multiplexing
- browser download behavior

### 22.5 Lifecycle Tests

- new share allocation
- polling delay
- update/password change
- expiration
- deletion during active stream
- agent reconnect
- gateway restart
- route snapshot replay
- origin tombstone persistence
- hostname collision handling

### 22.6 Abuse Tests

- connection flood per IP
- connection flood per origin
- wrong-password reporting
- shared CGNAT behavior
- IPv6 source rotation
- malicious agent false reports
- no cross-agent block poisoning
- active stream termination after block

### 22.7 End-to-End Browser Matrix

- Chrome desktop/mobile
- Safari macOS/iOS
- Firefox desktop/mobile where supported
- Immich native mobile link creation
- Nextcloud native mobile link creation after source support
- password-protected shares
- long video seek and resume
- owner offline and reconnect states

## 23. Alternatives Considered

### 23.1 Keep Current Secure Relay

Advantages:

- already works
- strongest reuse of existing effort
- browser-to-agent Noise encryption

Rejected as long-term default because:

- custom browser transport remains complex
- service-worker HTTP simulation remains fragile
- native video and WebSocket behavior remain difficult
- office application support becomes disproportionately complex

It remains the migration fallback.

### 23.2 Cloudflare Tunnel

Advantages:

- very simple
- reliable global infrastructure
- automatic browser certificates
- ordinary HTTP

Rejected as the primary privacy architecture because Cloudflare terminates browser TLS and can inspect plaintext content. It remains a possible opt-in mode for users comfortable with that trust model.

### 23.3 Permanent Per-Agent Origin

```text
files.<agent>.example
```

Rejected because a recipient who once learns it can continue sending TLS traffic toward the agent while any share remains active. The gateway cannot determine which encrypted HTTP share path is being attempted.

### 23.4 Independent Top-Level Origin Per Share

```text
<share>.sharebridgeusercontent.com
```

Provides stronger cross-share unlinkability but requires one certificate or shared platform wildcard key per share. A shared wildcard private key cannot be distributed to agents safely. Per-share public certificate issuance creates unacceptable scale and lifecycle complexity.

### 23.5 Per-Agent Wildcard With Per-Share Child Origins

Chosen:

```text
<share>.<agent-namespace>.sharebridgeusercontent.com
```

It provides exact per-share edge revocation with one certificate per agent.

### 23.6 zrok/OpenZiti

OpenZiti provides mature identity-aware encrypted service networking and zrok provides public/private sharing. It is substantially heavier operationally and its stock public frontend terminates browser TLS.

OpenZiti may become a future FRP replacement if ShareBridge requires multi-region routing, service-fabric failover, or richer network identity. It is not required for the first native-HTTPS data plane.

### 23.7 Generic Application Proxy

Rejected. ShareBridge origins remain bound to explicit native shares and connector-defined routes.

## 24. Operational Metrics

The system should measure without inspecting content:

- active agent tunnels
- active share origins
- connections per origin
- connections per agent
- connection failures by reason
- bytes per origin/account
- gateway-to-agent latency
- tunnel reconnects
- route propagation lag
- revocation propagation lag
- certificate issuance latency
- certificate renewal success
- days until certificate expiry
- CA provider errors
- blocked connection counts
- agent-reported auth failures

Logs must not record:

- passwords
- private keys
- full native share codes unless strictly required and protected
- file names or content
- authorization cookies

## 25. Rollout and Compatibility

- Existing shares remain on the legacy transport until explicitly migrated.
- Native HTTPS is initially opt-in/feature-flagged.
- The canonical native links do not change.
- The server records the transport mode per share during migration.
- Rollback switches canonical routing back to the legacy transport without changing the native source link.
- Agent upgrades prepare certificates and tunnels before enabling native HTTPS.
- A server must not redirect to an origin until the corresponding agent version confirms support.

## 26. Decisions Recorded

- Use ordinary browser HTTPS as the target data plane.
- Terminate browser TLS at the agent.
- Use raw SNI-based Layer 4 forwarding.
- Use FRP as the initial tunnel candidate behind a replaceable interface.
- Preserve the global `sharebridge.app` canonical native-link base.
- Use a separate content registered domain for browser isolation.
- Use one random public certificate namespace per agent.
- Use one random exact child origin per native share.
- Never reuse a share origin.
- Do not encode service type in the hostname.
- Do not rotate origins while the same native share remains active.
- Do not add redundant OTPs to ordinary native shares.
- Validate exact origin/type/code binding on the agent.
- Remove exact gateway routes upon source revocation.
- Use agent semantic reports plus gateway metadata for abuse controls.
- Keep CA selection provider-neutral.
- Begin certificate coordination as an internal worker with isolated interfaces.
- Run gateway/FRP separately from the control-plane web process.
- Migrate incrementally and retain the legacy data plane until parity.

## 27. Decisions Requiring Validation Before Implementation Commitment

These are validation tasks, not unspecified product behavior:

1. Select the content registered domain.
2. Prove nested wildcard DNS behavior with the intended DNS provider.
3. Confirm FRP can provide the required exact SNI/raw-TCP topology.
4. Select the real-client-IP/connection-ID mechanism.
5. Confirm ZeroSSL terms and operational limits for the intended workload.
6. Prove Google Public CA issuance and renewal with agent-generated wildcard CSRs.
7. Decide primary/fallback CA ordering from spike evidence.
8. Define route lease behavior during control-plane outages.
9. Benchmark certificate handshake overhead and tunnel throughput.
10. Decide whether the agent rotates its private key on certificate renewal.
11. Confirm the desired minimum supported browser/OS trust stores for CA chains.

Failure of a certificate or raw-TLS spike is a design blocker. It must be resolved before deleting or broadly replacing the current Secure Relay data plane.

## 28. Implementation Decomposition

This architecture is too large for one implementation plan. After approval, it should be decomposed into separately reviewed plans:

1. **Certificate and DNS spike**
2. **FRP raw-TLS/SNI gateway spike**
3. **Control-plane identifier and route model**
4. **Agent HTTPS server foundation**
5. **Immich native-HTTPS migration**
6. **Abuse reporting and edge enforcement**
7. **Nextcloud/OpenCloud migration**
8. **Legacy transport removal**
9. **Office collaboration spike**

No implementation slice should delete the working legacy path before its replacement passes the relevant parity and rollback gates.
