# Progressive Immich Gallery Design

## Problem

Large Immich albums currently load eagerly. A 2,453-item album sends roughly 492 KB of metadata, creates every tile in one synchronous HTML operation, initializes LightGallery against every DOM node, fetches every thumbnail from Immich, transmits every thumbnail, and retains every object URL. Live logs show thumbnail transfer alone taking 5–14 seconds, while the browser main thread becomes visibly unresponsive.

## Design

Keep the complete metadata list on both peers so the album count, Download All, direct item downloads, and full lightbox navigation remain available. Make tile rendering and thumbnail transfer demand-driven in fixed windows of 120 items.

The agent sends `thumbnail_list` metadata with `thumbnailMode: "pull-v1"` and does not immediately stream every thumbnail. A capable browser sends `thumbnail_batch_request` control messages containing a required unique request ID, start index, and count. The agent retains the gallery item list for the connection, fetches only the requested slice with the existing six-worker limit, and replies with indexed thumbnail frames followed by `thumbnail_batch_complete` containing the request ID, actual clamped start/count, success/failure counts, and explicit `failed_indices`. `sent + failed` always equals the actual count; media-lane send failures count as failed.

The agent starts a five-second legacy fallback after sending the list. A synchronized connection state makes exactly one transition from `waiting` to `pull` on the first valid request or from `waiting` to `legacy` when the timeout wins. Once legacy streaming starts, pull requests are rejected, so boundary races cannot produce duplicate streams. A pull-capable browser sends its initial request immediately after handling the list. If no request arrives, the agent streams all thumbnails and sends the existing `thumbnail_complete` message. This makes rolling deployment safe: a new browser recognizes the advertised ranged mode, while an old browser still receives the legacy stream; a new browser connected to an old agent sees no ranged-mode advertisement and continues accepting the old eager stream.

The browser initially renders 120 tiles and requests their thumbnails only when pull mode is advertised. An `IntersectionObserver` sentinel appends and requests the next 120 only after the preceding batch completes, so the agent has at most one thumbnail batch in flight. A visible Load More button uses the same path as an accessibility and unsupported-browser fallback. Requests are tracked as queued, in-flight, and complete by range and request ID so observer callbacks, button clicks, and repeated or out-of-order completion messages cannot duplicate work. Because control and media lanes can overtake one another, completion marks only `failed_indices` unavailable and leaves successful frames eligible to arrive late. During the unresolved first-pull compatibility boundary, any valid current-gallery thumbnail index is accepted so legacy fallback media that overtakes its control rejection is not lost; duplicate and out-of-metadata indices remain rejected.

LightGallery 2.9 runs in dynamic mode on a stable gallery container with `dynamic: true` and one `dynamicEl` entry per metadata item. Image entries start with the transparent placeholder `src`; video entries also carry the existing placeholder video metadata. Clicking a rendered tile calls `openGallery(globalIndex)`, so lightbox navigation can cross unloaded grid windows. Thumbnail and preview arrivals update `lightbox.galleryItems[globalIndex]` directly without rescanning or refreshing grid DOM. Preview requests and the existing active/neighbor video behavior remain unchanged.

## Resource Management

Only rendered windows receive thumbnail object URLs. Version 1 appends windows rather than virtualizing or evicting earlier ones: this removes the expensive initial 2,453-node render and spreads later DOM work across explicit scroll actions without introducing fragile responsive-grid spacers or scroll anchoring. Thumbnail and preview URLs use distinct `thumb:<id>` and `preview:<id>` ownership keys. A preview may replace the dynamic lightbox source while the grid retains its thumbnail. On replacement or destroy, LightGallery is destroyed first, then every owned blob URL is revoked exactly once. If live measurement still shows material slowdown only after scrolling through most of an album, bounded two-way virtualization will be designed as a separate change.

The existing thumbnail envelope carries a 16-bit index. The agent therefore caps advertised gallery metadata at 65,536 items and logs when it truncates a larger album. Pull requests allow 1–120 items, clamp the final window to the advertised list, and reject invalid or out-of-range requests. Only one batch may run at a time; additional concurrent requests receive a scoped error rather than spawning more worker pools. A completion makes its explicit failed indices terminal and leaves declared-success indices eligible until their media frames arrive. Failed tiles are shown as unavailable and are not automatically retried. Selective retry is deferred.

## Validation

Agent tests cover mode advertisement, legacy timeout fallback, atomic fallback cancellation, one-batch concurrency, the 65,536-item boundary, request validation, range clamping, ranged delivery, completion invariants, and no immediate eager stream. Browser tests cover both mixed-version directions, the 120-item initial window, progressive expansion, duplicate suppression, Load More fallback, request/completion correlation, global-index lightbox opening, cleanup, and URL revocation. Existing gallery download and preview/video behavior remains covered.
