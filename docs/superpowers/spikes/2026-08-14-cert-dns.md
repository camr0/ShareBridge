## Purpose

Prove the certificate + DNS half of direct-TCP: the agent generates its own TLS
key + a CSR for **both** wildcard SANs (key never leaves the agent), the control
plane's certificate coordinator completes ACME DNS-01 and returns only the
public chain, and a DDNS package manages the direct namespace's wildcard A
record. The code itself is enforced in-process (signature check, exact 2-SAN
enforcement, chain/key/SAN/EKU validation); the observational results below are
filled in by a manual run against a real Cloudflare zone + CA, which needs
operator-supplied secrets that are never committed.

## 5. Two-wildcard-SAN issuance behavior

`GenerateWildcardCSR` requests exactly two SANs in one CSR —
`*.<namespace>.<baseDomain>` (direct, default mode) and
`*.relay.<namespace>.<baseDomain>` (relay, FRP fallback). `CompleteCSR` verifies
the CSR's signature and enforces the exact two-SAN set (rejecting extras,
missing, duplicates, and any IP/email/URI SANs) before ordering, then finalizes
the agent's pre-made CSR via `ObtainForCSR`, so the coordinator never sees the
agent's private key. One order with two SANs = one certificate = no extra
rate-limit cost (spec §7/§8).

- Issued certificate SAN count: `[pending manual run]` (expected: 2)
- Orders consumed: `[pending manual run]` (expected: 1)
- Certificates consumed toward the weekly limit: `[pending manual run]` (expected: 1)

## 6. ValidateChain behavior

`ValidateChain` (agent-side) checks, in order: every PEM block parses and the
chain is non-empty; the chain verifies against the configured trust root with
the leaf as the server cert; the leaf's public key equals the locally-held key;
the SAN set is exactly the two wildcards; the leaf is currently valid; and the
leaf asserts serverAuth EKU + digital-signature key usage.

The negative cases are covered by unit tests and all pass (see the task report):

- self-signed leaf → rejected
- expired leaf → rejected
- wrong-key leaf → rejected
- extra SAN → rejected
- missing SAN → rejected

## 9. Account-key persistence requirement

The spike uses an **ephemeral** ACME account key (`acmeAccount.key`, regenerated
per call). Phase 2 **MUST** persist this key securely: it identifies the ACME
account, and losing it would orphan the account and break renewals. This is a
documented follow-up, not implemented in the spike (YAGNI — no production
wiring).

## 10. Renewal plan

Renewal reuses the same path as issuance: the agent generates a fresh key+CSR
for the same two wildcard SANs, the coordinator completes DNS-01, and the agent
validates + atomically reloads the chain. Renewal cadence (e.g. 30 days before
the 90-day LE expiry), atomic reload of the HTTPS server's cert, CA abstraction,
and CT handling are identical to the FRP spec (§8) and are out of scope for this
spike. The persisted ACME account key (§9) is the prerequisite for renewal.

## 11. How to run

```bash
# 1. Env (never committed)
export CLOUDFLARE_API_TOKEN='<single-zone DNS-edit token>'
export CLOUDFLARE_ZONE='<test zone>'
export ACME_EMAIL='<acme contact>'
export SPIKE_NS='v7q4km2x9pz6dn3w'
export SPIKE_BASE='<test base domain, e.g. sbx.example.com>'

# 2. Agent generates key.pem (0600) + csr.pem (two wildcard SANs)
cd agent && go run ./cmd/spike-certagent

# 3. Control plane completes CSR -> chain (staging first)
cd ../signaling-server
export ACME_CA='https://acme-staging-v02.api.letsencrypt.org/directory'  # default if unset
export CSR_FILE='../agent/csr.pem' CHAIN_FILE='../agent/chain.pem'
go run ./cmd/spike-cert

# 4. Agent validates the returned chain against the staging root
cd ../agent
SPIKE_CA_ROOT='<staging-root.pem>' go run ./cmd/spike-certagent -validate

# 5. DDNS create/update/delete + propagation
cd ../signaling-server
export SPIKE_DDNS_NAME='*.v7q4km2x9pz6dn3w.sbx.example.com'
export SPIKE_PROBE_NAME='probe.v7q4km2x9pz6dn3w.sbx.example.com'
export SPIKE_DDNS_IP='<agent-ip>' SPIKE_DDNS_IP2='<second-ip>'
go run ./cmd/spike-ddns

# 6. Repeat 2-4 against production only after staging succeeds
export ACME_CA='https://acme-v02.api.letsencrypt.org/directory'
#   (agent -validate uses SPIKE_CA_ROOT=<production ISRG root>)
```
