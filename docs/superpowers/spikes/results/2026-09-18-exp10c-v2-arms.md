# Experiment 10c — v2 relay arms (EAST ×2, WEST ×2, browser-sink if cheap) — 2026-09-18

**Verdict:** E10's single 233.285 Mbps v2 relay cell was **not a lucky moment**: two fresh CLIENT-EAST cells gave **233.694** and **233.507 Mbps** (three cells across two sessions spread **0.18%**). The never-before-measured **CLIENT-WEST** v2 relay arms gave **228.379** and **214.882 Mbps** — **3.57–3.79× the v1 baseline of 60.24 Mbps**, and no worse than EAST. The **browser-sink arm worked**: a real Chromium downloaded at **239.054 Mbps** through the same relay, so v2's advantage is not an artefact of using `curl`. v1's ceiling roughly halves when RTT goes 12 → 71 ms (111 → 60 Mbps); v2's barely moves (233.6 → 221.6 Mbps). The v1 rig was restored and verified.

**Setup:** v2 = the deployed phase-4a TEST systemd stack on TESTBOX (`sharebridge` control on
`:8080`, `sharebridge-relay-frps`, `sharebridge-relay-gateway` on `:443` SNI passthrough) plus the
TEST v2 agent container `sharebridge-agent-test` on VERSA. Method replicated byte-for-byte from
Experiment 10's successful 233.285 Mbps cell: bring the v2 units up, `POST
/api/shares/<code>/prepare-route` on the control loopback, then fetch the asset **from the relay
origin URL that `prepare-route` returns** (`status=relay`, `relay_url`), streaming exactly
790,626,304 B (754 MiB) into a byte-count sink. Payload volume 790,626,304 B = 6,325.01 Mb per cell,
agent → client, same client VMs and hour as the v1 arms. Hosts are named only VERSA / TESTBOX /
CLIENT-EAST / CLIENT-WEST.

## Interpretation

**1. The v2 CLIENT-EAST number is stable, and E10's cell was representative.** 233.694, 233.507
(this run) and 233.285 (E10) span 0.18%. Against E10's 110.97 Mbps v1 arm that is **2.106×**; against
the lowest v1 EAST cell (102.02) it is 2.291×. Mean 233.50 Mbps = **94.9%** of the ~246 Mbps path
reference.

**2. The decision-relevant gap is filled, and it favours v2 more strongly than EAST did.** CLIENT-WEST
had never been measured on v2. It came in at **228.379 / 214.882 Mbps** (mean 221.63, best 92.8% of the
path) versus v1's **60.24 Mbps** — a **3.57–3.79×** ratio, larger than EAST's 2.10–2.29×.

**3. The mechanism is RTT insensitivity, not just a lower absolute cap.** Across the same two client
hosts and the same payload volume, v1 falls from ~111 Mbps at ~12 ms to ~60 Mbps at ~71 ms (≈**0.54×**),
while v2 goes from 233.60 to 221.63 (≈**0.95×**). v1's WebRTC/SCTP path degrades with RTT; the v2 relay's
TCP does not. That is the strongest single statement this experiment supports.

**4. The client is not the v2 constraint.** Every v2 cell sampled `vmstat` idle at **100%**, versus 23%
idle for the v1 EAST cell in E10. Consistent with Exp 9 / E8b's conclusion that v1's ceiling lives in the
client-side WebRTC sink, not in the hosts or the path.

**5. The relay hop was near its own ceiling.** Mid-transfer `ss` samples on the agent→relay FRP data
connection showed `delivery_rate` 226–246 Mbps with cwnd climbing 237 → 999. So the residual 5–10% gap to
the 246 Mbps reference is path/TCP dynamics on the relay→client leg, not an available software headroom
item.

**6. The browser arm removes the curl asymmetry and costs nothing.** 239.054 Mbps with a real Chromium
download sink — *above* the curl cells, which is consistent with the browser window excluding connection
setup and TLS handshake that the curl window includes. There is no evidence that v2 throughput depends on
the client being a non-browser HTTP client.

## Caveats

- **Not a byte-identical comparison.** The v2 TEST image holds only Immich shares, and only 2 of its 11
  active shares had an original ≥ 790,626,304 B. Those cells stream exactly 790,626,304 B from the start of
  a larger original (1,445,795,840 B and 1,240,955,392 B) and the client stops the stream at the byte
  bound (curl exit 23 / EPIPE). Volume, client, direction, hour and network path match v1; the *source
  object* does not. The gateway-counter overshoot (0.33–0.65%) is that truncation, and the retained
  retransmissions on the FRP connection at each cell end are its tail, not path loss.
- **Small n.** n=2 per client this run (n=3 for EAST including E10). EAST's spread is 0.18%, but WEST's two
  cells differ by **5.91%** (228.379 vs 214.882), so the WEST mean is the least precise number here; the
  WEST *range* is the honest statement.
- **Relay only.** All 11 active shares returned `status=relay`, and the agent's `direct_status` is
  `relay_fallback`, so every number here is the relay path. Nothing is established about a future direct
  path, and the ~246 Mbps reference is itself a reference, not a measured simultaneous ceiling.
- **Browser cell volume differs** by 1.83× (the agent ignores `Range`, verified), so it is a rate-for-rate,
  not byte-for-byte, comparison; a complete download also commits one ledger download.
- **VERSA retransmit counters are not attributable** — they are host-global and include unrelated
  production traffic on the same box. Only the CLIENT-EAST/WEST counters and the per-connection `ss`
  samples are meaningful here.
- Single TEST namespace, single TEST relay deployment. One transient was observed: a
  `prepare-route` call returned a body with no `status` field and succeeded on immediate retry; no cell was
  ever run off a transient response.
- Both arms are browsers, but the sinks still differ: the v1 arm used the application's own download sink
  on the v1 WebRTC path, while this arm used Chromium's download manager on the v2 relay path. The
  asymmetry measured here is browser-vs-`curl` on the v2 side, which is what E10 left open.
