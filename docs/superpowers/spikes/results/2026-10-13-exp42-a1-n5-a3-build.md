# Experiment 42 — A1 / N5 / A3 bulk-transport build (2026-10-13)

**Status:** code complete and unit-tested on the agent side. **A3 is field-testable today.**
**A1 and N5 are agent-side mechanisms only and are NOT safe to enable until the matching client
transport lands** (§6). No field run, no `docker build`, no lab harness, no `git` command, and no
access to VERSA/TESTBOX/clients was used for this experiment — this is a build + unit-test result,
not a throughput result.

**Verdict:** the three levers are implemented behind `SB_BULK_*` env flags, off by default, with the
default path pinned byte-identical. A3 (pacing) needs no client change. A1/N5 add v2 chunk envelopes
and a round-robin reorder that a native Go receiver handles today and the browser does not yet.

**Setup:** `benchdirect` worktree only (`agent/`, Go 1.26.1 darwin/arm64;
`signaling-server/web/` for the JS reorder module). Nothing else touched.

## 1. Flags

| flag | lever | default | accepted | meaning |
|---|---|---|---|---|
| `SB_BULK_CONNS` | **A1** | `1` (off) | int 1–4 (clamped) | independent PeerConnections carrying one transfer |
| `SB_BULK_LANES` | **N5** | `1` (off) | int 1–8 (clamped) | ordered bulk DataChannels on the one association |
| `SB_BULK_PACE_MBPS` | **A3** | `0` (off) | float ≥0 (clamped ≤10000) | token-bucket rate for bulk sends, Mbit/s |

Parsing follows the `SB_SCTP_*` / `sctpEnvUint` convention in `internal/peer` (note: that helper lives
on the `e2e-v1` branch, not on `benchdirect`, whose `peer.go` predates it — `bulkfan` mirrors the
convention exactly: unset → default; unparseable or below-minimum → log `bulkfan: ignoring …` and keep
the default; above-maximum → log `bulkfan: clamping …`). `Config.Enabled()` is false iff every lever
is at its default, and the manager takes its untouched path in that case.

## 2. What each lever does

### A1 — `SB_BULK_CONNS` (N independent PeerConnections)
- `multilane.FanoutChannelSet` presents one logical channel set whose bulk lane comes from several
  endpoints (control/media stay on the primary set).
- `transfer.stripedEndpoint` round-robins bulk chunk frames across the lanes and rewrites each frame
  from the 14-byte v1 envelope to a 22-byte **v2 envelope carrying a global uint64 chunk sequence**.
- `bulkfan.ReorderBuffer` / `ReorderBuffer.Push` reassembles by that sequence.

### N5 — `SB_BULK_LANES` (K ordered streams on one association)
- `peer.Peer.CreateOffer` creates `bulk`, `bulk-1`, … `bulk-(K-1)` DataChannels; `Peer.BulkEndpoints()`
  returns them in striping order; readiness waits for every stripe lane.
- Same `stripedEndpoint`/v2 envelope/reorder as A1 — SCTP head-of-line blocking is per-stream, so a
  loss stall is confined to 1/K of the flow.

### A3 — `SB_BULK_PACE_MBPS`
- `bulkfan.TokenBucket` (50 ms burst, floored at one 64 KiB chunk) paced inside
  `Manager.sendWithBackpressure`, which every bulk caller already routes through.
- Independent of A1/N5 and **requires no client change**: the wire format is unchanged.

## 3. Default-path identity — how it was verified

1. **Wire format pinned by an existing test.** `manager_test.go:712` asserts the exact v1 bytes of
   `encodeChunkFrame`; that function was not modified. `bulkfan.EncodeChunkFrame` (v2) is only reached
   from `stripedEndpoint`, which is only constructed when a lever is enabled.
2. **New tests prove the levers are inert by default:**
   - `TestBulkEndpointsNilInDefaultConfiguration` — no extra lanes, `BulkEndpoints()==nil`.
   - `TestManagerLeversOffByDefault` — with all three env vars unset, `m.bulk == m.rawBulk`
     (not `*stripedEndpoint`) and `m.bulkPacer == nil`.
   - `TestFanoutChannelSetWithoutBulkEndpointsDelegates` / `…SingleBulkLaneReportsNil` — the A1 wrapper
     degenerates to the primary set.
3. **Read-path audit:** `readyForHandshakeLocked()` reduces to the original
   `len(opened)==len(requiredLanes) && !handshakeArmed` when `extraBulk` is empty; `pace()` returns
   immediately when `bulkPacer` is nil; `discoverBulkEndpoints()` leaves the endpoint list empty unless
   a channel set advertises >1 lane. No call sites in `manager.go` changed shape.

## 6. Client-side status — the part that is NOT done

Enabling `SB_BULK_LANES` or `SB_BULK_CONNS` against the **current browser** does not work, and I did
not pretend otherwise:

- **N5:** `channelSet.js` `attach()` accepts only `control`/`media`/`bulk` and *fails the whole set* on
  an unknown label, so `bulk-N` lanes must be accepted and routed; `app.js` must reorder per operation
  before `appendChunk` (wireBytes still counts arrivals). The tested `bulkReorder.js` is the intended
  drop-in; it is **not yet wired into `app.js`**, and `binaryEnvelope.js` still rejects envelope v2
  (its test asserts that rejection).
- **A1:** additionally needs (a) daemon peer-creation (`createPeer` currently makes one `Peer` per
  `connID`), (b) capability negotiation so an un-updated browser is never sent a second offer, and
  (c) signaling round-trip of `peer_id` (`agent_ws.go` strips it from the offer; `browser_ws.go` stamps
  `connID` on the answer), plus (d) browser fan-in over N PeerConnections. None of these were built.

**Recommendation:** field-test **A3 only**. Treat A1/N5 as agent-side ready pending the client work.

## 8. Caveats

- Nothing here was measured. The mechanisms are unproven; the review's honest priors stand
  (A1 ≤1.2× at 12 ms, 1.0–1.8× at 70 ms; A3 0–20%).
- `stampChunkSequence` decodes and re-encodes every chunk (two copies) on the flagged path only —
  a CPU cost that is off by default and untested at field rates.
- `SB_BULK_CONNS`'s only agent-side effect today is the striper decision plus the log line, because
  nothing yet creates the second association (§6a).
